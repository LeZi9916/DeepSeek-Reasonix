重启后上下文占用先显示得偏高、聊一轮又落回的问题已修复。

## 修复

- 重启或切换回一个会话时，上下文占用直接显示上次退出时的真实大小。此前这一读数依赖进程内存里的两项状态：供应商上次报告的 prompt 大小，以及据此学到的分词比例；两者在重启后丢失，读数退回按字符冷估算的近似值，直到下一轮回复才回落（63f4e2122）
- 冷估算偏高的主因是中文标点按拉丁字符计价：`，。！？「」《》` 和全角空格不在 CJK 判定范围内，各占 3 字节、按每 4 字节一个 token 计，实际却通常几个标点才一个 token。本次没有改这条计价规则；这项修复只是让重启后不再退回冷估算（63f4e2122）
- 这两项状态改为随会话保存到 `<id>.prompt-usage.json`，并在恢复会话时读回。记录带模型名与折叠版本号：换了模型、或在此之后又折叠过，旧记录不会被当成当前上下文的读数（63f4e2122）

## 升级须知

- 升级后第一次打开旧会话仍会先显示冷估算值，因为此时还没有这份记录；此后每次保存会话都会写入，从那时起重启读数一致（63f4e2122）

Fixes the context figure reading high right after a restart and dropping once you send a message.

## Fixed

- A restarted or reopened session now shows the size it last reported from the provider. That reading depended on two things held only in process memory — the provider's last prompt count and the tokenizer ratio learned from it — and both were lost on restart, so the figure fell back to a character-based cold estimate until the next reply (63f4e2122)
- The cold estimate overcounts Chinese text mostly because of punctuation: `，。！？「」《》` and the ideographic space fall outside the CJK range, so each is priced as 3 bytes at four bytes per token, though a mark usually costs a fraction of a token. This release does not change that pricing rule; it stops the estimate from being used after a restart (63f4e2122)
- Both values are now saved beside the conversation in `<id>.prompt-usage.json` and read back on resume. The record names the model and the fold generation it was measured under, so a record from another model or from before a later fold is not reused as the current reading (63f4e2122)

## Upgrade notes

- The first open of an older conversation after upgrading still shows the cold estimate, because no record exists yet. Every session save writes one from then on, and restarts agree from that point (63f4e2122)
